Instrumented 8K delivery

Prism

Prism is an instrumented platform for producing live 8K broadcasts and delivering them to the screens. It takes a real contribution — a cinema camera or its own instrumented source — encodes it, packages it on its own low-latency origin, and delivers it globally, measuring true per-stage latency the whole way. Because every frame carries its own timestamp (stamped in, or filmed off an optical slate), Prism measures all of this without guessing.

The measurement model

One timecode, followed from the lens to the screen

Every frame carries a QR timecode stamped with its emission epoch. Latency at any point is simply that frame's own age when it is seen there — no cross-clock arithmetic, no assumptions. With a real camera there are two references, kept separate on purpose: pipeline latency (T0→T6, from the encoder's stamp) and glass-to-glass (acquisition + pipeline, from the scene itself). The acquisition stage exists because of the camera slate page — a full-screen QR clock (with stamp-hold and sync bands) that any display can show and any camera can film, putting real-world time onto the glass itself.

Post-decode

Precise stages catch the exact frame (frame-level age); freshness stages read the newest served frame. Acquisition is deliberately not a T-stage: it is a same-frame differential — a frame that shows the filmed slate AND carries the encoder's stamp yields camera→capture time with the observer's clock cancelled out — and it carries its own error sources (display lag, exposure, slate↔encoder clock agreement), stated in every report. Measured on the real camera days: latency numbers are lens-referenced off the glass, not just encoder-referenced. A warm-up window keeps pipeline spin-up out of the numbers, and every run resets to zero, so results reflect steady state — not the first noisy seconds.

Capabilities

What it does

The whole chain in one platform — origination or real-camera contribution through playback, with the instrumentation an ordinary encoder can't provide.

Originate

Generate the source — or film it

A test pattern, a pre-rendered file, the instrumented QR-timecode source — or a real camera filming the slate page, a full-screen QR clock that puts scene time on the glass. Any resolution up to 8K.

Encode

Hardware or software

NVENC H.264 / HEVC / AV1 or libx264/libx265, with presets, rate control, and split-frame encoding across multiple NVENC engines for 8K. Never falls back to CPU silently.

Deliver

CMAF, SRT, origin, CDN

CMAF (HLS + DASH) to disk, an SRT contribution, and Prism's own low-latency origin — LL-HLS with real blocking reloads and 0.25 s parts plus LL-DASH from one CMAF chunk set, a four-rung ladder (bit-exact 8K HEVC, 4K HEVC, 1080p + 720p H.264) with up to 4×7.1 audio, Apple-conformant — with CloudFront in front.

Measure

Per-frame latency

QR-timecode latency across T0→T6 — precise where the exact frame can be caught, freshness where only the newest segment is visible — plus the acquisition differential when a camera films the slate, so glass-to-glass is measured from the scene, never inferred.

Span continents

Distributed probes

Passive probes on separate instances — including CDN-edge boxes on the US East Coast and in Europe — measure real cross-network hops with clock-synced one-way timing.

Operate & observe

Console + monitor + self-check

An always-on seven-view console (fleet control, live ops with egress-surface health and event log, five-step test builder, typed Reports with two-run diffing), the hosted Confidence monitor with per-channel audio meters, and a one-click instrument health check. Every run writes a diffable report; quality is scored per run with VMAF v1 + CAMBI at the one lossy boundary.

What you put it to

What it lets you test

The questions a delivery pipeline actually raises — answered on real hardware and a real network, with numbers you can trust and compare.

Throughput

Real-time headroom

Can this GPU hold 1× (or N×) at a given resolution, frame rate, codec, and preset? Live speed, fps, and drop telemetry answer it on the actual instance — e.g. 8K60 HEVC at 1.0×.

End to end

Glass-to-glass latency

The true source→viewer delay, with a per-stage breakdown — encode vs. SRT vs. packaging vs. delivery vs. player — so you can see which latency dominates.

Across the wire

Cross-machine latency

Measure a genuine SRT contribution between instances, over the real network, with the one-way timing that only synchronized clocks make honest.

Trade-offs

Codec & config A/B

Sweep any mix of codec, preset, resolution, frame rate, segment duration, and bitrate; every report embeds its configuration and diffs directly against another.

Integrity

Timecode survivability

Confirm the QR survives the encode at a given bitrate and resolution before trusting any number — a pass/fail gate, not a guess.

Integrity

Known-delay calibration

Inject a measured delay at one stage and confirm that only that stage moves — the correlation check that makes the whole chain believable.

The rig

Hardware & cloud

The validated results run on AWS EC2 — a small fleet spanning three regions — but nothing here is AWS-specific.

Encoder

NVIDIA L40S · g6e

Three NVENC engines drive the split-frame 8K60 encode; runs the headless campaign engine the console relays to.

Mux + ladder

NVIDIA L4 · g6

Receives the SRT contribution, packages CMAF / HLS for the local T3 reading, builds the four-rung GPU ladder and sends it as one transport stream over SRT to the origin — without ever touching the encoder's pace.

Origin

LL origin · m6i

A CPU box running Prism's own packager and LL-HLS / LL-DASH server: the segment window lives in RAM, sessions splice cleanly, and it powers on and off with the fleet. CloudFront pulls from it.

Control plane

Console · t3.small

Always on — the only box that is: TLS + per-user auth, the pipeline graph, fleet start/stop, campaign relay, the hosted player, and the instrument health check. Survives fleet power-cycling.

Real player

Windows + L40S · g6e

Chrome with hardware HEVC Main10 decode — the only way to watch the 8K rung in a browser (Linux Chromium has no HEVC). It reads the QR off its rendered frame and reports T6.

CDN edges

Probe boxes · 2 continents

Small CPU instances in us-east-1 and eu-central-1 decode the QR straight off their local CloudFront edge. They power on and off with the fleet — zero standby cost between runs.

AWS glue

Time Sync · CloudFront

The Amazon Time Sync Service keeps chrony µs-accurate (what makes cross-machine timing honest); CloudFront fronts the origin — HTTP/2 only (Apple's validator objects to HTTP/3 on the master), error caching off for the live edge. No managed packager anywhere.

Not AWS-locked

Prism is Python + FFmpeg + NVENC/NVDEC, so it runs on any Linux GPU host, and its origin is its own process — no managed packager to substitute. The AWS pieces map straight across: EC2 GPU instances → GCP A3/G2 or Azure NV/NC series; the Time Sync Service → any chrony/PTP/NTP source; security groups → the platform's firewall controls; CloudFront → any CDN that honours the origin's cache headers. Same rig, different cloud.

  • Player race mode — LL-HLS, HLS, and DASH playing the same stream side by side, each with its own latency readout.

Reach & production

Exploratory

The larger platform Prism is growing toward.

  • Hardware PTP clock — the on-prem contributor disciplined by a GPS PTP grandmaster, tightening lens-referenced timing further. Hardware specified and priced; the camera chain itself is now proven (see Validated).
  • Super-resolution, census-first — frontier upscalers measured honestly on the fleet GPU: the first census point puts diffusion-based 4K→8K at ~0.12 fps (~500× off real time) on a single 48 GB card via 2×2 tiling. Realtime remains a 1080p→4K story; venue-scale needs multi-GPU tiling. The curve, not the hype, drives what ships.
  • Venue playout integration — a real venue media server pulling LL-HLS / LL-DASH from the origin, closing the last hop.
  • More edge regions — the two-continent probe fleet is live and one script-run per region to grow (Asia-Pacific, South America).
Honest by design

Every stage is labeled measured, derived, or not measured — Prism never presents an estimate as a measurement. T1/T2 are measured per frame on the instrumented path; T3–T5 are freshness readings taken wherever a real endpoint serves (per part on the low-latency lane); T6 is read off a real browser's rendered frame. When the instrument itself was the problem — as its own health check proved once, and as the part matcher and the DASH manifest clock proved since — the numbers were corrected and the old ones retracted. What it can't observe cleanly, it says so.
